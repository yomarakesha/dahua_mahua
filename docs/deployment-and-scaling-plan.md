# План развёртывания и масштабирования (multi-site)

_Черновик стратегии. Составлен 2026-07-03. Язык: русский (технические термины / команды — на английском)._

## Из чего состоит приложение (текущая архитектура)

4 сервиса + БД, сейчас — Windows-службы через NSSM за одним TLS-прокси:

| Сервис | Роль | Технология | Порт |
|---|---|---|---|
| **Backend** | «Мозг»: NVR/камеры/пользователи, RBAC, JWT-авторизация, **дирижирует go2rtc** (пишет ему конфиг), плейбек (ffmpeg→fMP4), warm pool, watchdog | FastAPI/Python + SQLite/Postgres | 8000 |
| **go2rtc** | Медиасервер: RTSP с камер → браузер (MSE/WebRTC), ffmpeg-перекодирование | Go + ffmpeg | 1984 / 8553 / 8556 |
| **Caddy** | TLS-обратный прокси, фронт для всего | Go | 8443 |
| **Frontend** | UI (статическая сборка React), раздаётся Caddy | React SPA | — |

Поток: `камеры → go2rtc → браузер`; backend стоит сбоку как управляющий (в live-видео не участвует; для **плейбека** — сам мини-медиасервер). Ценность (IP) — почти вся в **backend** и в накопленном опыте, не во фронтенде.
(MediaMTX — legacy, `relay="go2rtc"`, выключен. Планируется удалить.)

## Ключевой вывод про «кражу» и свой сервер

- **Веб-фронтенд спрятать нельзя**; `.exe` (Electron/Tauri) кладёт тот же JS внутрь — тоже извлекается. Десктоп = UX, не секретность.
- Для VMS backend+go2rtc **обязаны крутиться на объекте клиента** (камеры в LAN, 4MP нельзя гнать наружу) → **код физически у клиента при любом раскладе**.
- Значит цель: не «сделать невозможным украсть», а «невыгодно красть + лицензирование».
- **Своего сервера для ПРОДУКТА не нужно** — он on-prem. Свой (крошечный) сервер нужен только для опционального «центра управления» (лицензии/обновления/удалённый доступ).

## Модель: «Appliance + Control plane»

1. **Appliance** = весь стек в **Docker Compose** (backend + go2rtc + caddy + Postgres + фронт), один `docker compose up` на объект, конфиг через `.env` под объект. Это и есть «динамично запускается на любом сервере».
2. **Лицензирование** — подписанная (Ed25519), привязанная к объекту, истекающая лицензия; backend проверяет встроенным публичным ключом. Копия образа без лицензии не запускается. Это реальный барьер, не обфускация.
3. **Control plane** (опц., позже) — крошечный VPS: онлайн-проверка лицензий (phone-home + kill-switch), OTA-обновления, реестр объектов, телеметрия, relay удалённого доступа.
4. **Frontend** — локальный веб-апп (работает в LAN даже без облака); опц. Tauri-обёртка для десктопа с авто-апдейтом и выбором сервера (как UX).
5. **Хардининг backend** — Nuitka/Cython или переписать секретные алгоритмы на Go/Rust (сдерживание, не стена).

## Реальность «нет своего сервера»

Не блокирует продукт (он on-prem). Разбивка:
- **Продукт** → на машине клиента. Ноль инфраструктуры у нас.
- **Лицензия v1** → офлайн-файл, подписанный нашим ключом. Ноль сервера.
- **Control plane / обновления / удалённый доступ** → когда будем готовы: VPS ~$4–6/мес (нагрузка мизерная — подписывает токены, отдаёт манифесты). Удалённый доступ — **Tailscale / Cloudflare Tunnel** (бесплатно), без своего сервера.
- **Железо на объекте:** либо клиент даёт свой ПК/сервер, либо продаём мини-ПК (Beelink/NUC ~$150–300) с образом.

## Дорожная карта (по шагам)

1. **Контейнеризация** стека в Docker Compose, портируемо под Linux (миграция с Windows/NSSM — учесть `C:\ffmpeg`, Job Objects, WinRM-специфику). ← первый шаг, разблокирует всё.
2. **Офлайн-лицензии**: генерация подписанных файлов нашим ключом; проверка в backend на старте. Базовая защита без сервера.
3. **При продажах:** VPS $5 → онлайн-лицензии (phone-home) + OTA-обновления + удалённый доступ (Tailscale/Cloudflare).
4. Решить модель железа (клиент даёт / продаём коробку).
